# M7 — Jouer par Internet (GameNetworkingSockets + edifice-lobby)

Objectif : un joueur héberge une partie depuis chez lui, elle apparaît dans l'onglet **Internet** de l'écran Join, et les autres la rejoignent **sans ouvrir de port**, avec des échanges **chiffrés**. Le LAN et l'IP directe continuent de marcher comme aujourd'hui.

Briques déjà en place : GameNetworkingSockets 1.6.1 via vcpkg avec ICE (STUN/TURN) validé sur les trois OS (#12), le serveur `edifice-lobby` (liste, sessions, signalisation authentifiée, STUN/TURN — #13, image ghcr.io #18), la sérialisation explicite (#14).

## Principe : GameNetworkingSockets comme simple « tuyau » sous `Sock`

Le protocole du jeu repose sur `Sock` : groupage de messages, canal fiable maison avec ses accusés de réception et ses *callbacks* (`RECEIVEDLANDINFO`…), un port par client côté serveur, filtrage par IP. Tout réécrire au-dessus des messages GameNetworkingSockets serait long et risqué.

On garde donc `Sock` tel quel et on remplace seulement **l'envoi et la réception de datagrammes** :

```
multiplay.cpp  ──  Sock (framing, fiabilité, callbacks : inchangés)
                        │
                 DatagramLink (nouveau)
                  ├── UdpLink : sendto/recvfrom, comme aujourd'hui (LAN, IP directe)
                  └── GnsLink : messages non fiables sur une connexion GameNetworkingSockets
                                (chiffrée, P2P via ICE, relais TURN si besoin)
```

- Une connexion GameNetworkingSockets par client. Les « ports » actuels (port d'info, port par client) deviennent un octet de canal en tête de chaque message, pour multiplexer sur la connexion unique.
- Chaque connexion reçoit une pseudo-adresse (`SOCKADDR_IN` unique) pour que le code existant (filtre par IP, `dest`, liste des serveurs) fonctionne sans changement.
- Double fiabilité (la nôtre par-dessus UDP chiffré) : un peu de surcoût, aucun risque de régression. Optimisation possible plus tard en passant les messages fiables au canal fiable de GameNetworkingSockets.

### M7b, réalisé (`src/net/gnslink.cpp`, `netlink.cpp`)

- **Choix du transport** : `transport=gns` dans `net.ini` (ou `HK_TRANSPORT=gns`), défaut `udp`. Build `EDIFICE_GNS=OFF` : UDP seulement, fil inchangé.
- **Canaux** : chaque message GameNetworkingSockets (non fiable, sans Nagle) = `[uint8 canal][datagramme de Sock]`, canal 0 = port d'info (REQUESTINFO, INFO, REQUESTENTER, ENTER), canal 1 = port du client (tout le reste). Le numéro de port d'ENTER reste envoyé mais n'ouvre rien.
- **Pseudo-adresses** : côté client, l'adresse demandée (IP du serveur, port d'info) ; côté serveur, l'IPv4:port distant de la connexion (0.0.x.y si elle n'en a pas, pour M7d).
- **Ports** : l'hôte écoute sur `gnsport` (défaut `datasendport`, laissé libre par l'UDP). La recherche LAN et les pairs UDP restent sur le socket UDP du port d'info : un serveur gns accepte les deux, un client gns n'utilise GameNetworkingSockets que pour les serveurs demandés par IP.

## Déroulé d'une partie Internet

1. **Au lancement** : `POST /v1/sessions` → identité (`str:edifice-…`), jeton, serveurs STUN/TURN avec identifiants. Connexion TCP au port de signalisation (`IDENTITÉ JETON`).
2. **L'hôte** démarre un serveur : `CreateListenSocketP2P`, puis `POST /v1/servers` (nom, version, protocole, joueurs, visibilité, identité) et renouvellement toutes les 20 s ; `DELETE` à la fermeture.
3. **Le client** : onglet Internet = `GET /v1/servers?protocol=N` ; il rejoint par `ConnectP2PCustomSignaling(identité de l'hôte)`. Les messages ICE transitent par le serveur de signalisation ; la connexion s'établit en direct, ou via TURN.
4. Ensuite tout passe par `GnsLink` : handshake de version, LANDINFO, jeu, vocal… exactement comme en LAN.
5. Visibilité : `public` (listée), `friends`/`private` (non listée, rejointe par un **code de partie** = id du serveur à partager).

### M7d, réalisé (`src/net/gnssignal.cpp`, `signaling.cpp`, `gnslink.cpp`, `netlink.cpp`)

- **Sessions** : l'hôte d'une partie Internet en ouvre une au démarrage du serveur (comme en M7c) ; le client, au moment où il rejoint une partie qui a une identité, pas avant (lister les parties n'envoie rien de plus au lobby). Une session par lancement du jeu, partagée par l'hôte et le client, renouvelée après 11 h. Sans GameNetworkingSockets (ou avec `p2p=0`), pas de session : l'hôte s'annonce sans identité et se rejoint en UDP direct.
- **Identité** : GameNetworkingSockets démarre sans identité, celle de la session lui est donnée ensuite (`ResetIdentity`, qui ferme connexions et écoutes ouvertes : les écoutes par IP sont rouvertes).
- **Identités garanties par le lobby** (changement du serveur) : `POST`/`PUT /v1/servers` portent aussi `session`, le jeton de la session de l'identité annoncée ; le lobby ne liste l'identité que si le jeton correspond, sinon la partie est listée sans identité (jamais renvoyé). Le client ne se connecte qu'à l'identité que le lobby liste pour la partie choisie (liste ou code).
- **Signalisation** : un client sur le modèle de `trivial_signaling_client.cpp` de Valve, dans un thread (`gnssignal.cpp`) : une connexion TCP au relais, `IDENTITÉ JETON` en première ligne, puis `DESTINATAIRE CHARGE` avec la charge en hexadécimal comme chez Valve. Adresse du relais : `signaling` de la session (nouveau champ, `-public-host` et le port de `-signal`), sinon l'hôte de l'URL du lobby, port 10000. Connexion seulement quand il y a un signal à envoyer ou qu'on héberge ; reconnexion avec un délai croissant (1 s à 30 s ; 60 s après un refus du jeton). File d'envoi bornée (64 lignes) ; une ligne de plus de 4 000 caractères n'est pas envoyée (le relais couperait la connexion).
- **Contrôles à la réception** (tout ce qui vient du relais passe par `signaling.cpp`, testé par `signaling_test` et fuzzé par `fuzz_signaling`) : lignes bornées et strictes (identité `str:` puis lettres, chiffres, `.`, `_`, `-` ; hexadécimal de longueur paire) ; le signal (protobuf `CMsgSteamNetworkingP2PRendezvous`, lu par un petit lecteur borné) doit avoir pour `from_identity` l'expéditeur garanti par le relais ; un client ne prend que les signaux des hôtes auxquels il se connecte ; une demande de connexion n'est prise que si l'on héberge, et seulement si l'identité qui la fait est cet expéditeur (sinon ignorée, sans réponse). GameNetworkingSockets vérifie ensuite que les signaux d'une connexion viennent de son identité distante, et la connexion est chiffrée de bout en bout (certificats non signés, faute d'autorité : c'est le relais authentifié qui garantit les identités).
- **Jeton de session** : jamais écrit dans les journaux ; il ne part qu'au lobby. Limite (levée ensuite, voir « Durcissement du lobby ») : la signalisation était du TCP en clair, le jeton y passait donc en clair.
- **STUN/TURN** : ceux de la session, passés à l'ICE natif de GameNetworkingSockets en valeurs globales (`P2P_STUN_ServerList`, `P2P_TURN_ServerList`, `…UserList`, `…PassList`) avant de créer écoutes et connexions P2P. Les URL du lobby (`stun:hôte:port`, `turn:hôte:port?transport=udp`) sont converties en `hôte:port` ; TURN sur TCP refusé (l'ICE natif ne le fait pas) ; virgules et espaces refusés (listes séparées par des virgules).
- **net.ini** : `p2p=1` (défaut), `p2p=0` (jamais : UDP direct comme en M7c), `p2p=relay` (seulement des candidats relais TURN, `P2P_Transport_ICE_Enable`) ; `HK_P2P` a priorité ; `HK_GNS_DEBUG=1` affiche les messages de GameNetworkingSockets. Le P2P ne dépend pas de `transport` : avec `transport=udp`, le lien d'info devient un `GnsLink` sans écoute ni connexion par IP, pour le P2P seulement (hôte d'une partie Internet ; client au moment de rejoindre).
- **Pseudo-adresses** : côté client, la connexion P2P est nommée par l'adresse et le port d'info que le lobby liste, si bien que l'écran Join retrouve la réponse INFO comme en UDP ; côté hôte, toujours 0.0.x.y (« Joueur at 0.0.0.1 requests to connect »).
- **Replis** : pas de GameNetworkingSockets, `p2p=0`, partie sans identité, session impossible (10 s au plus) : UDP direct. Si ICE échoue (GameNetworkingSockets abandonne après 10 s), la connexion se ferme et les demandes d'info suivantes partent en UDP direct ; l'écran Join attend 20 s en tout. Le relais TURN est choisi par ICE quand rien d'autre ne passe.
- **Tests** : `tests/net_p2p.py` (job CI `gns`, Linux) lance le lobby avec son TURN, puis en direct et en relais seul (`p2p=relay` des deux côtés) : deux processus `tests/gns_p2p_test.cpp` (`GnsLink` seul, connexion chiffrée, directe ou relayée selon le drapeau `Relayed` de GameNetworkingSockets), puis un hôte du jeu et un deuxième jeu qui le rejoint par son code (P2P vers l'identité listée, chiffré, direct ou relayé, LANDINFO, hôte qui le voit en 0.0.x.y et en compte 2 joueurs). **Limite** : tout tourne sur une machine, sans NAT entre les joueurs, et sur son adresse LAN (GameNetworkingSockets n'accepte pas les adresses de bouclage pour ICE, relais TURN compris). La signalisation, ICE, le relais TURN et le jeu par-dessus sont testés ; la traversée de NAT réelle (NAT symétrique, CGNAT) ne l'est pas : à vérifier à deux machines sur deux réseaux, avec l’instance publique.

### Durcissement du lobby (suite de M7d, `server/websocket.go`, `api.go`, `gnssignal.cpp`)

- **Signalisation en WebSocket** : le relais est aussi servi sur l'API HTTP (`GET /v1/signal`, RFC 6455), donc derrière le reverse proxy HTTPS de l'instance publique (Caddy relaie les WebSocket d'office) : `wss://`, sans deuxième certificat ni deuxième port, et le jeton ne passe plus en clair. Mêmes messages que le TCP, une ligne par trame texte ; le jeton dans la première trame (`IDENTITÉ JETON`) plutôt que dans un en-tête, pour qu'aucun journal de proxy ne l'enregistre ; mêmes limites (4 Ko, 50 messages/s, 5 min d'inactivité), trames non masquées ou fragmentées refusées, pings répondus. Les deux transports se parlent (un client WebSocket joint un hôte TCP).
- **Choix du transport** : la session donne `signaling_url` (`wss://hôte/v1/signal`, déduit de `Host` et `X-Forwarded-Proto`, ou de `-public-url`) en plus de `signaling` (TCP, inchangé pour les anciennes versions). Le jeu prend le WebSocket quand il a libcurl, sinon le TCP ; `HK_SIGNAL_TCP=1` force le TCP (tests). Le relais TCP se coupe avec `-signal off`, une fois toutes les versions en circulation passées au WebSocket (puis fermer le port 10000).
- **libcurl** : l'API WebSocket de curl (`curl_ws_send`/`recv`, `CONNECT_ONLY=2`) n'existe que depuis 7.86 et est restée expérimentale, absente de la plupart des builds, jusqu'à 8.11 : ni l'Ubuntu 22.04 (7.81) ni le curl système de macOS (8.7.1) ne l'ont. Le jeu se sert donc de curl pour TCP + TLS seulement (`CONNECT_ONLY=1`, `curl_easy_send`/`recv`, ALPN limité à HTTP/1.1), et fait la mise à niveau et le tramage lui-même (`signaling.cpp`, testé par `signaling_test`, fuzzé par `fuzz_signaling`) : marche avec tous ces curl (Windows : 8.10.1 compilé, inchangé), sans rien vendoriser de plus. Le certificat est vérifié comme pour le reste du lobby ; `EDIFICE_TEST_CA_FILE` (tests seulement) ajoute un certificat auto-signé de confiance, sans jamais couper la vérification.
- **Adresses privées refusées** : une annonce dont l'adresse vue est privée, de bouclage, link-local ou CGNAT (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, 100.64/10, ::1, fc00::/7, fe80::/10) reçoit un 400 explicite ; le journal du lobby suggère `EDIFICE_TRUST_PROXY=1` (c'est l'adresse du proxy qu'il voit). `-allow-private` pour le LAN et la CI.
- **`X-Forwarded-For`** : l'entrée **la plus à droite** qui n'est pas un de nos proxys (`-trusted-proxies`, IP/CIDR ; par défaut un seul proxy, celui qui se connecte : la dernière entrée), au lieu de la première, qu'un client invente à volonté quand le proxy ajoute à l'en-tête. Tests Go des cas d'usurpation.
- **Tests** : Go (relais WebSocket ↔ TCP, poignée de main RFC 6455, trames refusées, `X-Forwarded-For`, adresses privées, `FuzzReadFrame`) ; `tests/net_p2p.py` lance le lobby en HTTPS avec un certificat auto-signé : la paire directe de `gns_p2p_test` et les jeux signalent en `wss://`, la paire relayée en TCP. **Non vérifié** : le passage par le Caddy de l'instance publique (à voir au déploiement), et le WebSocket du jeu Windows (même code, curl/Schannel, pas de test P2P sous Windows en CI).

### M7e, réalisé (`build.py --gns`, `.github/workflows/release.yml`, `tests/check_package.py`)

- **Releases avec GameNetworkingSockets** : le job `build` compile les trois archives avec `python build.py --config Release --gns --package --test` (`--universal` sur macOS). L'adresse du lobby reste celle de l'instance publique par défaut (`lobby=https://edifice.rousseaufournier.com` dans `data/net.ini`) ; `p2p=1` par défaut : choisir l'onglet Internet suffit, rien à ouvrir chez l'hôte.
- **vcpkg** : épinglé (`VCPKG_COMMIT` dans le workflow, aussi pour le job `gns`), cache binaire de vcpkg (`VCPKG_DEFAULT_BINARY_CACHE`) gardé par `actions/cache`, clé = commit de vcpkg + `vcpkg.json` + `cmake/triplets/`. Triplets release seulement (`x64-linux-release`, `x64-windows-release` et `universal-osx` de `cmake/triplets/`) : deux fois moins à compiler.
- **macOS** : un seul binaire universel arm64 + x86_64, triplet `universal-osx` (bibliothèques statiques pour les deux architectures ; OpenSSL s'y compile sans assembleur). Rien à copier dans `Frameworks` (`macos_bundle_fixup.cmake` le ferait pour une dylib), signature ad hoc inchangée. Minimum inchangé : macOS 10.13 en Intel, 11.0 en Apple Silicon (le premier qui existe). Les SDK récents préviennent que leur libc++ ne prend plus en charge moins de 11.0 (simple avertissement) ; rien n'est testé sur un vieux macOS.
- **Linux** : GameNetworkingSockets, protobuf, abseil et OpenSSL en statique (triplet x64), libcurl du système comme avant, compilé sur ubuntu-22.04 (glibc 2.35). Les symboles des bibliothèques statiques ne sont pas exportés (`-Wl,--exclude-libs,ALL`, trouvé par le durcissement du lobby, déjà dans `CMakeLists.txt`) : sans cela, la libssl du système (chargée par libcurl) se lie à l'OpenSSL de GameNetworkingSockets au lieu de sa libcrypto et tout HTTPS vers le lobby échoue. `check_package.py` vérifie qu'aucun symbole OpenSSL n'est exporté et fait une vraie requête HTTPS depuis l'archive (voir plus bas). macOS n'est pas concerné (espace de noms à deux niveaux : la libcurl du système se lie à ses propres bibliothèques), Windows non plus (GameNetworkingSockets a sa `libcrypto-3-x64.dll`, curl est en Schannel).
- **Windows** : triplet DLL (`/MD`, le triplet statique ne se lie pas) ; vcpkg copie `GameNetworkingSockets.dll`, `libprotobuf.dll`, `abseil_dll.dll`, `libcrypto-3-x64.dll`… à côté de l'exécutable, CMake y ajoute les DLL du runtime C++ (`InstallRequiredSystemLibraries` : `vcruntime140*.dll`, `msvcp140*.dll`…, déploiement local autorisé par les conditions de redistribution de Visual Studio), et `build.py` met toutes les DLL du dossier dans l'archive. L'UCRT fait partie de Windows 10 et plus. libcurl passe au runtime partagé lui aussi (`CURL_STATIC_CRT` seulement sans GameNetworkingSockets).
- **Licences** : dossier `licenses/` dans chaque archive, rempli par `build.py` : textes de GameNetworkingSockets (BSD-3), protobuf (BSD-3), abseil (Apache-2.0), OpenSSL (Apache-2.0), utf8-range, SDL2 (zlib), opus (BSD) et curl (Windows). Le jeu reste sous LGPL v3.
- **Test de chaque archive** (`tests/check_package.py`, étape du job `build`) : décompression, contenu (données, licences), dépendances (macOS : `lipo`, `otool -L`, versions minimales, `codesign --verify` ; Linux : `readelf`/`ldd`, aucune bibliothèque de GameNetworkingSockets en dynamique ni symbole OpenSSL exporté ; Windows : `dumpbin /dependents` de chaque exe et DLL, tout doit être dans l'archive ou dans Windows, et jamais le runtime C++ de System32), puis le jeu décompressé lancé en serveur (`HK_AUTOSTART=1`, `HK_TRANSPORT=gns` : « gns: listening on port », qui demande GameNetworkingSockets et OpenSSL) et `tests/net_handshake.py` contre lui (sous Windows, un simple avertissement : les runners n'ont que l'OpenGL 1.1 de Windows et le jeu s'y arrête peu après le démarrage du serveur ; le lancement y prouve que toutes les DLL se chargent et que GameNetworkingSockets démarre). Sous Linux en plus (`--lobby`), une vraie requête HTTPS depuis l'archive : un `edifice-lobby` local en TLS (certificat auto-signé, `EDIFICE_TEST_CA_FILE`), où le jeu, en `servervisibility=public`, doit être listé avec son identité P2P et écouter en P2P (« gns: listening for P2P connections as »). La release (`needs: [build]`) dépend donc de ces vérifications ; les tests P2P (job `gns`) restent hors du chemin de la release.
- **Non vérifié** : un Windows propre sans redistribuable (le runner en a un ; `dumpbin` garantit seulement qu'aucune DLL du runtime n'est prise ailleurs que dans l'archive), un vieux macOS (10.13) ou un Mac Intel réel, d'autres distributions Linux que celle du runner, et toujours la traversée de NAT réelle entre deux réseaux.

## Décisions à prendre

1. **Requêtes HTTPS vers le lobby depuis le jeu** : libcurl (via vcpkg, comme GameNetworkingSockets) ou un petit client HTTP maison si le lobby reste en HTTP derrière un tunnel. Recommandation : **libcurl** (TLS correct sur les 3 OS).
2. **Adresse du lobby par défaut** : nom de domaine de ton instance (à fournir), modifiable dans `net.ini`.
3. **Runtime Windows** : passer tout le jeu en `/MD` quand GameNetworkingSockets est activé (DLL), et livrer les DLL du runtime dans l'archive.
4. **Code de partie** pour les parties privées/amis : l'id du serveur (16 caractères hex) ou un code plus court (6 caractères) généré par le lobby.

Décidé (M7c) : **libcurl** (système sur macOS et Linux, compilé avec Schannel sur Windows ; sans libcurl l'onglet Internet le dit) ; adresse du lobby dans `net.ini` (`lobby=`, vide en attendant l'instance publique) ; **code court** : l'id d'une partie est un code de 6 caractères (sans 0/O ni 1/I), recherche insensible à la casse et limitée par IP. La session est ouverte au démarrage du serveur plutôt qu'au lancement du jeu (rien n'est envoyé au lobby tant qu'on n'héberge pas en Internet) ; le client n'en a pas encore besoin (M7d). L'hôte choisit sa visibilité dans Server Setup (`servervisibility`, `lan` par défaut) ; la connexion reste l'UDP direct (ports à ouvrir chez l'hôte) jusqu'à M7d.
