# Build d'Edifice (HugeKilla)

Un seul code pour les trois systèmes : **SDL2** (fenêtre, entrées, audio) + **sokol_gfx** (Metal sous macOS, Direct3D 11 sous Windows, OpenGL 4.1 core sous Linux ; voir « Rendu sokol_gfx »), ou l'**OpenGL 2.1** d'origine (profil legacy, fixed-function) avec `--gl`, gardé le temps d'une release.
SDL2 est téléchargée et compilée **en statique** par CMake (`FetchContent`, SDL 2.32.10), de même que libopus 1.5.2 (codec du chat vocal, licence BSD) : les binaires ne dépendent que du système.

| OS | Résultat |
|---|---|
| macOS (Intel / Apple Silicon) | `Edifice.app` autonome (données dans `Contents/Resources/data`), signé ad hoc |
| Linux | `Edifice` + dossier `data/` à côté |
| Windows (MSVC, x64) | `Edifice.exe` + dossier `data/` à côté, CRT statique (avec `--gns` : DLL de GameNetworkingSockets et du runtime C++ à côté) |

`build.py` compile avec GameNetworkingSockets par défaut, comme les releases, pour le P2P des parties Internet : sans `VCPKG_ROOT`, il récupère vcpkg dans `build/vcpkg` (au commit `VCPKG_COMMIT` de la CI) ; le premier build compile ses bibliothèques (OpenSSL, protobuf, abseil), les suivants les réutilisent. `--no-gns` compile sans (parties Internet en UDP direct).

## Prérequis

Seulement la chaîne de compilation (+ Python 3) ; pas besoin d'installer SDL2.

- **macOS** : `xcode-select --install`, puis `brew install cmake ninja`
- **Linux (Debian/Ubuntu)** :
  ```bash
  sudo apt install build-essential cmake ninja-build libglu1-mesa-dev libx11-dev libxext-dev libxrandr-dev libxcursor-dev libxi-dev libxss-dev libwayland-dev libxkbcommon-dev libasound2-dev libpulse-dev libcurl4-openssl-dev
  ```
  (les en-têtes X11/Wayland/audio servent à compiler SDL ; à l'exécution SDL charge ce qui est présent ; libcurl sert à la liste des parties Internet, le jeu se compile sans, l'onglet Internet dit alors qu'il n'est pas disponible)
- **Windows** : Visual Studio 2019+ (charge « Développement Desktop en C++ »), CMake (fourni avec VS), Python 3. libcurl (liste des parties Internet) est téléchargé et compilé avec le TLS de Windows (Schannel), comme SDL2 ; `-DEDIFICE_LOBBY=OFF` s'en passe.

## Compiler

```bash
python3 build.py                     # Release avec P2P (GameNetworkingSockets) dans build/<os>-release-gns
```

```bash
python3 build.py --config Debug --run
```

```bash
python3 build.py --package           # dist/Edifice-<version>-<os>.zip|.tar.gz
```

Sous Windows : `py build.py ...`. Options : `--clean`, `--test` (tests unitaires après le build), `--generator <G>`, `EDIFICE_ARCH=Win32` pour du 32 bits, `--universal` (macOS : un binaire arm64 + x86_64, macOS 10.15 minimum, comme la release), `--no-gns` (sans GameNetworkingSockets, donc sans P2P : plus rapide à compiler, mais les parties Internet demandent des ports UDP ouverts ; voir ci-dessous), `--gl` (rendu OpenGL fixe au lieu de sokol_gfx, dans `build/<os>-<config>[-gns]-gl` ; un dossier de build configuré avant la bascule passe à sokol_gfx au build suivant). `EDIFICE_CMAKE_ARGS="-D…"` ajoute des arguments CMake.
`-DEDIFICE_SYSTEM_SDL2=ON` (CMake) utilise une SDL2 installée au lieu de la compiler.
La version vient de `project(Edifice VERSION …)` dans `CMakeLists.txt`.

Avec les presets CMake : `cmake --preset macos-release && cmake --build --preset macos-release` (ou `linux-release`, `windows-vs` / `windows-release`, et `web` pour la version web, voir plus bas).

```bash
python3 build.py --web --run         # version web (Emscripten) dans build/web, servie sur http://127.0.0.1:8000/
```

## Tests

- `ctest --test-dir build/<os>-release -C Release` : tests unitaires sans fenêtre (valeurs de référence du générateur du monde, `tests/worldrandom_test.cpp` ; lecture/écriture little-endian bornée de `src/net/wire.h`, `tests/wire_test.cpp` ; message VOICE, règles de distance et aller-retour opus, `tests/voice_test.cpp` ; cartes sauvegardées : aller-retour, fichiers corrompus, tronqués ou trop gros refusés, sauvegardes d'origine construites à la main, `tests/map_test.cpp` ; SHA-256 et HMAC-SHA256 contre les vecteurs FIPS 180-2 et RFC 4231, et le cookie du handshake, `tests/hmac_test.cpp` ; manette : zone morte, courbe, stick vers déplacement, déplacements du focus des menus, `tests/input_test.cpp`), lancés par la CI sur les trois OS. `map_test --check <fichier>` dit si un fichier est une carte valide.
- Tests réseau contre un serveur local (`HK_AUTOSTART=1 <binaire> &`, puis) :
  - `python3 tests/net_handshake.py` : version dans INFO, refus des versions incompatibles ;
  - `python3 tests/net_identity.py` : une nouvelle demande garde son slot, un autre client a le sien ;
  - `python3 tests/net_join.py` : rejoint la partie comme un vrai client et décode PLAYERNAMES, LANDINFO, SERVERVARS, etc. (tailles et valeurs du format explicite), puis envoie des messages tronqués ;
  - `python3 tests/net_fuzz.py` : paquets malformés, à lancer de préférence contre un build AddressSanitizer (voir l'en-tête du script) ;
  - `python3 tests/net_voice.py` : trois clients ; la voix n'est relayée qu'au joueur proche, sous le numéro de l'émetteur, et jamais si le message est malformé ;
  - `HK_AC_VARS="ac_cookietime=1000 ac_ipenter=600" python3 tests/net_cookie.py` (le serveur lancé avec le même `HK_AC_VARS`), puis avec `ac_requirecookie=1` dans `HK_AC_VARS` et l'argument `require` : cookie du handshake (`docs/M11.md`, phase 2), pas de slot sans cookie valide, réponse jamais plus grosse que la demande, ancien client accepté ou refusé selon `ac_requirecookie` ;
  - `python3 tests/net_map.py --write /tmp/test.map`, puis `HK_AUTOSTART=1 HK_MAPFILE=/tmp/test.map <binaire> &` et `python3 tests/net_map.py /tmp/test.map` : un client qui rejoint un serveur lancé avec une carte reçoit son relief, son ciel et tous ses blocs.
  - `HK_ANTICHEAT_LOG=1` sur le serveur, puis `python3 tests/net_slots.py <stderr du serveur>` : slots stables et positions numérotées (`docs/M11.md`, phase 3b), départs et arrivées avec des clients nouveaux puis un ancien ;
  - `tests/run_netplay_tests.sh <binaire>` lance ces tests et `net_anticheat.py`, un serveur neuf par test (sous Linux avec Xvfb si aucun écran) ; à lancer en local (pas dans la CI), de préférence contre un build AddressSanitizer + UBSan (voir « Sanitizers et avertissements »).
- Manette (local, pas dans la CI) : `python3 tests/input_smoke.py <binaire> [--out dossier]` joue des appuis scriptés (`HK_PADTEST`, manette virtuelle de SDL) dans un dossier utilisateur à part (pas de lobby, `servervisibility=lan`, ports 37320/37321) : marche au stick (analogique), regard, arme suivante, tir, jetpack, menu de construction, pause, débranchement et rebranchement à chaud, écran d'apparition, menus au focus (Options → Pad / Touch, Server Setup, Join, menu de construction), commandes tactiles (marcher, regarder et tirer à trois doigts, pause et reprise, toucher sur l'écran d'apparition et dans les menus) ; captures PNG dans `--out`.
- Partie à deux sur une machine : `HK_AUTOSTART=1 <binaire> &` puis `HK_JOIN=127.0.0.1 <binaire>` (le second rejoint le premier serveur qui répond). `HK_CONSOLE_LOG=1` recopie la console sur stderr. `HK_ANTICHEAT_LOG=1` écrit sur stderr les événements anti-triche du serveur (`docs/M11.md`). `HK_AC_VARS="ac_requirecookie=1 ac_cookietime=1000"` (noms `ac_*`, séparés par des espaces) remplace les valeurs de `sv.ini` pour ces variables du serveur.
- Parties Internet (lobby, M7c) : `python3 tests/net_lobby.py <binaire> <edifice-lobby> [<lobby_test>]` (Linux, avec un écran ou `xvfb-run`) lance le lobby de `server/`, un hôte qui s'y annonce et un client qui le rejoint par son code de partie ; `HK_LOBBY_URL=http://127.0.0.1:8080 lobby_test` teste seul le client du lobby.
- Même réseau : `python3 tests/net_lan.py <binaire> <edifice-lobby> [p2p]` lance le lobby derrière deux petits proxys qui font venir les requêtes de deux adresses publiques différentes ; un hôte annonce son adresse LAN, un joueur « de la même adresse publique » doit la recevoir et rejoindre par elle, l'autre ne doit la voir ni dans la liste ni par le code (macOS et Linux avec un écran ; il faut une adresse IPv4 privée sur la machine).

Parties Internet : dans `net.ini`, `lobby=https://…` donne l'adresse du serveur `edifice-lobby` (par défaut l'instance publique `https://edifice.rousseaufournier.com` ; `lobby=` vide coupe les parties Internet, et l'onglet Internet de l'écran Join dit alors qu'aucun lobby n'est configuré), et `servervisibility=lan|public|friends|private` (ligne « Internet » de Server Setup) dit si l'hôte s'annonce : `public` est listée, `friends`/`private` se rejoignent par le code de partie (6 caractères, affiché dans la console et le tableau des scores de l'hôte). Avec GameNetworkingSockets (`EDIFICE_GNS`, ci-dessous), une partie Internet se rejoint en P2P (M7d) : rien à ouvrir chez l'hôte. Sans lui (ou avec `p2p=0`), c'est l'UDP direct vers l'IP vue par le lobby, et l'hôte doit ouvrir ses ports UDP (27020 et suivants). Deux joueurs derrière le même routeur : l'hôte annonce aussi ses adresses LAN, que le lobby ne donne qu'aux joueurs venant de la même adresse publique ; ils le voient « LAN 192.168.x.y » dans l'onglet Internet et le rejoignent par là (la plupart des routeurs ne renvoient pas vers le LAN ce qui vise leur propre IP publique ; détails dans `docs/M7.md`).

## Sanitizers et avertissements

Le jeu se compile sans `-fwrapv`, `-fno-strict-aliasing` ni `-Wno-return-type` (M12.6) : un dépassement d'entier signé, un accès par un type incompatible ou une fonction qui ne rend rien sont des bugs, que UBSan signale. Build instrumenté (le code du jeu ; SDL, opus et curl restent tels quels) :

```
EDIFICE_CMAKE_ARGS="-DCMAKE_CXX_FLAGS=-fsanitize=address,undefined -DCMAKE_EXE_LINKER_FLAGS=-fsanitize=address,undefined" python3 build.py --config Debug
```

Puis `ctest` (dans `build/<os>-debug-gns`), `tests/run_netplay_tests.sh <binaire>` (échoue sur un rapport AddressSanitizer ; chercher aussi `runtime error` dans les logs) et une courte partie (`HK_CONSOLE=notify HK_SHOT=… HK_SHOT_FRAME=600`, avec un `HK_USERDIR` à part). Sous macOS, le `.app` ne trouve pas `libclang_rt.asan_osx_dynamic.dylib` : la copier de `$(xcrun --find clang)/../../lib/clang/*/lib/darwin/` dans `Edifice.app/Contents/MacOS/`.

`-DEDIFICE_WERROR=ON` fait de tout avertissement du jeu et de ses tests une erreur (`-Werror`, `/WX` sous MSVC) ; le code tiers (SDL, opus, curl, GNS) a ses propres cibles et n'est pas concerné. La CI compile ainsi sur les trois systèmes (`EDIFICE_CMAKE_ARGS` dans `release.yml`) ; hors CI l'option est désactivée, un compilateur plus récent pouvant avertir davantage. Restent désactivés, sur du code des années 2000 : `-Wno-write-strings`, `-Wno-parentheses`, `-Wno-dangling-else`… (liste dans `CMakeLists.txt`), `/W1` sous MSVC, `-fpermissive` sous GCC.

## Rendu sokol_gfx (M13)

Par défaut depuis M13.4, comme dans les releases (CMake : `-DHK_RENDER_SOKOL=ON`, l'option ; `python3 build.py --gl` ou `-DHK_RENDER_SOKOL=OFF` revient au backend OpenGL fixe, `renderer_gl.cpp`, le temps d'une release : pour une machine sans OpenGL 4.1 ni Direct3D 11) : le rendu passe par [sokol_gfx](https://github.com/floooh/sokol) (`renderer_sokol.cpp`) sur l'API du système : **Metal** sous macOS, **Direct3D 11** sous Windows, **OpenGL 4.1 core** sous Linux. `-DHK_SOKOL_BACKEND=GLCORE` compile aussi le chemin Linux sous macOS, pour l'essayer. Le reste du jeu ne change pas : il dessine par `renderer.h` dans les deux cas.

- `src/third_party/sokol/sokol_gfx.h` : en-tête unique, licence zlib (`LICENSE`), commit `170136d` de floooh/sokol (12 octobre 2026), sans modification ; compilé seul dans `sokol_gfx_impl.cpp` (en Objective-C++ avec ARC sous macOS), sans `-Werror`.
- Shaders : `src/render/shaders/edifice.glsl`, en GLSL annoté de `sokol-shdc`, converti au build en `build/…/shaders/edifice.glsl.h` (Metal, HLSL 5, GLSL 4.10, et déjà GLSL ES 3.00 et WGSL pour le web, M14). CMake télécharge `sokol-shdc` une fois pour la machine qui compile, depuis floooh/sokol-tools-bin au commit `b975d56` (celui du 11 octobre 2026, accordé à `sokol_gfx.h`), et vérifie son SHA-256 ; `-DHK_SOKOL_SHDC=<chemin>` en utilise un déjà installé (build hors ligne). Metal et HLSL sont compilés au lancement du jeu (pas d'outils Xcode ou Windows nécessaires au build ; Windows fournit `d3dcompiler_47.dll`).
- `sokol_native.cpp` fait ce que sokol_gfx laisse à l'application : la fenêtre SDL (`SDL_WINDOW_METAL` et une `CAMetalLayer` ; une swapchain DXGI sur le `HWND`, sur WARP s'il n'y a pas de GPU ; un contexte GL 4.1 core), la présentation, la VSync, la taille en pixels (Retina), et les relectures (`HK_SHOT`, captures d'écran, profondeur sous le soleil) : sokol_gfx n'en a pas, elles passent par l'API (blit Metal vers un buffer partagé, texture `STAGING` D3D11, `glReadPixels` sur un framebuffer à nous).
- Une image est d'abord enregistrée (sommets convertis en listes de triangles et de lignes, une commande par lot avec son pipeline et ses uniformes), puis dessinée dans une image hors écran quand elle est présentée ou relue ; la fenêtre en reçoit une copie. Lignes larges et points (que seul OpenGL dessinait) deviennent des quads face à l'écran ; `glClear` devient un quad au plan lointain. Les textures sont générées avec les mêmes mipmaps que `gluBuild2DMipmaps` (`texture_sokol.cpp`).
- Une build Debug valide chaque appel sokol_gfx (et chaque erreur GL sous Linux) : les messages commencent par `sokol_gfx` sur stderr. `python3 tests/render_smoke.py <binaire ou .app> [--out dossier] [--ref dossier]` dessine les menus et une partie, et échoue sur une erreur de sokol_gfx (les avertissements sont seulement affichés), une image unie ou un jeu qui s'arrête (la CI le fait, en Debug).
- Non reproduit : l'antialiasing des lignes (`RCAP_LINESMOOTH`, les étincelles) ; ces lignes sont dessinées pleines.

## Graphismes Ultra (expérimental)

Options → Video/Audio → **Graphics : Classic / Ultra** (`graphics=ultra` dans `control.ini`, Classic par défaut ; `HK_GRAPHICS=ultra|classic` le remplace pour un essai). Un second chemin de rendu dans le backend sokol_gfx (`src/render/renderer_ultra.cpp`, shaders `src/render/shaders/ultra.glsl`, convertis par `sokol-shdc` en Metal, HLSL 5 et GLSL 4.10) : la scène 3D dans une image HDR (RGBA16F), éclairée par le soleil en PBR (Cook-Torrance GGX, métal/rugosité) avec l'ambiance du ciel, ombres en cascades (atlas 2×2, PCF), ciel par diffusion atmosphérique (Rayleigh et Mie, LUT calculée sur le CPU, teintée par la couleur de brouillard de la carte), brouillard de hauteur, eau à vagues de Gerstner (réflexion plane, réfraction, absorption selon l'épaisseur d'eau, écume, reflets du soleil, vue sous l'eau), herbe instanciée qui ondule au vent, arbres de la carte qui se balancent, puis bloom, rayons de soleil (god rays), petit lens flare, exposition, ACES et FXAA, sous le HUD dessiné comme avant. Textures HD dans `data/hd/` (voir son `README.md` : générées par FLUX.1 schnell, Apache-2.0, cartes dérivées par `tools/hd_textures.py`), chargées seulement en Ultra.
- Le jeu dit seulement ce qu'il dessine (`RSetMaterial` : terrain, blocs, modèles, feuillage) et où la scène commence et finit (`RUltraBegin`/`RUltraEnd`, `RUltraWater`, `RUltraGrass`, `renderer.h`) ; en Classic ces appels ne font rien (pas de changement d'état, pas de lot coupé) : le rendu Classic reste identique au pixel près.
- **Arbres, buissons et rochers** (« Ultra: trees and rocks » Off/Near/Far, `ultravegetation`, `src/render/ultra_veg.inl`) : maillages faits au lancement (conifères en cônes, feuillus et buissons en boules bosselées, rochers en sphères déformées, chacun avec une version légère au loin), placés chaque image autour de la caméra par un hachage de la case et du relief (hauteur, pente, eau) : les mêmes chez tous les clients, plus denses en forêts, rochers plus nombreux sur les pentes et les rives, jamais dans un bloc ni à moins de 12 à 14 unités d'un drapeau ou d'une station. Ils oscillent au même vent que l'herbe, projettent des ombres et se reflètent dans l'eau. **Purement visuels** : pas de collision, rien sur le réseau ; un joueur Ultra peut donc ne pas voir derrière un arbre un joueur que voit un joueur Classic (et inversement, on ne se cache pas pour de vrai derrière un arbre).
- Sous-options : « Ultra: shadows » Off/Low (2 cascades, atlas 2048)/High (4 cascades, atlas 4096), « Ultra: grass » Off/Low/High, « Ultra: water » Sky only/Reflections (`ultrashadows`, `ultragrass`, `ultrawater` dans `control.ini`).
- Pas en Ultra : le backend OpenGL fixe (`--gl`), la version web (WebGL2, sans cibles flottantes partout ; `data/hd` n'est pas empaqueté), la vue stéréo. Les nénuphars ne sont pas dessinés en Ultra (ils couleraient dans les vagues) ; les vagues sont visuelles, l'eau du jeu reste à `WATERHEIGHT`.
- Aides : `HK_ULTRA_SUN=<hauteur>` change la hauteur du soleil en Ultra seulement (0.06 : coucher), `HK_SKY=N` choisit le ciel N de `skies.ini`, `HK_CAMERA="x,z,hauteur,cap,tangage"` (ou `HK_CAMERA=lake`, la rive d'un lac proche) dessine depuis ce point (le joueur ne bouge pas) ; `tests/render_smoke.py` dessine aussi deux scènes Ultra.

## Version web (M14)

Le jeu tourne dans un navigateur, compilé par **Emscripten** en WebAssembly : WebGL2 (sokol_gfx, GLSL ES 3.00), son par SDL2 (Web Audio), réglages dans IndexedDB. En solo, et en **joueur d'une partie Internet hébergée par une version de bureau** (M14, tâche 3) : le navigateur n'a pas d'UDP, il rejoint l'hôte par un DataChannel WebRTC (voir plus bas). L'onglet Internet grise les parties dont l'hôte ne prend pas les navigateurs (version plus ancienne, ou compilée sans `EDIFICE_WEBRTC`). Une partie hébergée dans le navigateur n'est jamais annoncée (`servervisibility` y vaut toujours `lan`) : il faudrait le même pont côté JavaScript.

```bash
python3 build.py --web               # build/web : index.html, index.js, index.wasm, index.data
python3 build.py --web --run         # la sert sur http://127.0.0.1:8000/ (EDIFICE_WEB_PORT) et ouvre le navigateur
python3 build.py --web --test        # + tests unitaires, compilés aussi en WebAssembly et lancés par Node.js
python3 build.py --web --package     # dist/Edifice-<version>-web.zip (le site, prêt à copier sur un serveur web)
```

- **emsdk** : `build.py --web` prend celui de `EMSDK` (après `source <emsdk>/emsdk_env.sh`), sinon il clone emsdk dans `build/emsdk` et y installe la version de la CI (`EMSDK_VERSION` de `release.yml`, 6.0.12). Il faut aussi `ninja`. À la main : `cmake --preset web && cmake --build build/web` (preset `web`, toolchain d'Emscripten trouvée par `EMSDK`).
- **Sans threads** : GitHub Pages ne peut pas envoyer les en-têtes COOP/COEP qu'exige `SharedArrayBuffer`, donc ni pthreads, ni libcurl (thread du lobby), ni GameNetworkingSockets dans cette build (`EDIFICE_GNS` y est refusé). Le lobby passe par le `fetch` du navigateur (`emscripten_fetch`, `-sFETCH=1`, `src/net/lobby.cpp`) derrière la même interface que curl ; le lobby doit autoriser l'origine de la page (CORS : `EDIFICE_CORS_ORIGINS` de `server/`, par défaut `https://nicrf.github.io`). Pour un lobby de test local, `-cors-origins http://127.0.0.1:8000` (l'origine de `build.py --web --run`). Les sockets UDP deviennent un lien sans UDP (`WebRtcLink`, `src/net/webrtclink.cpp`) : une partie solo garde son serveur local, qui n'envoie rien, et une partie Internet passe par WebRTC.
- **Boucle** : `main()` initialise puis rend la main au navigateur (`emscripten_set_main_loop`) ; `Frame()` (`src/platform/platform_sdl.cpp`) est un passage de la boucle, le même en natif (appelé en boucle par `main()`) et sur le web (une fois par image du navigateur, donc à la VSync). Pas de sommeil quand la fenêtre n'a pas le focus : le navigateur suspend lui-même un onglet masqué.
- **Fichiers** : `data/` est préchargé en mémoire (`--preload-file`, `index.data`, environ 19 Mo), en lecture seule sous `/data`. Le dossier utilisateur est `/user`, un système de fichiers IndexedDB (IDBFS) que `src/platform/web/pre.js` monte et charge avant `main()` : `net.ini`, `control.ini`, `sv.ini` (copiés de `data/` au premier lancement) et `maps/`. Ce que le jeu y écrit est réenregistré au plus une fois par seconde (`HKFilesWritten`, `fileio.h`), et quand la page est masquée ou quittée.
- **Page** : `src/platform/web/shell.html` (la page, un canvas plein écran que SDL suit quand la fenêtre change de taille ; progression du chargement ; message si WebGL2 manque) ; le son démarre au premier clic ou à la première touche (règle des navigateurs). La souris est capturée (pointer lock) au clic ; Échap la rend au navigateur et ramène au menu, comme Échap en natif. Plein écran : F6.
- **Rendu** : `sokol_native.cpp` crée un contexte WebGL2 par SDL (ES 3.0, sans alpha : la page ne transparaît pas). WebGL2 ne relit pas la profondeur : le soleil n'est jamais caché par le relief dans cette build.
- **Aides au debug** : les variables `HK_*` (voir « Aides au debug ») se passent dans l'URL, par exemple `http://127.0.0.1:8000/?HK_MENU=serverstart&HK_SEED=42`.
- **Réseau (M14, tâche 3)** : rejoindre une partie Internet ouvre une session de lobby (identité, jeton, STUN/TURN), puis le relais de signalisation du lobby par WebSocket (`signaling_url`, `wss://…/v1/signal`) et un `RTCPeerConnection` avec un DataChannel `edifice` non ordonné et sans retransmission (`maxRetransmits: 0`) : l'offre, la réponse et les candidats ICE passent en lignes `rtc1:` sur ce relais (`src/net/signaling.h`), puis le protocole du jeu passe tel quel sur le DataChannel (`src/net/webrtclink.cpp`, objets du navigateur dans `src/platform/web/webrtc.js`, `--js-library`). L'hôte de bureau répond par libdatachannel (`src/net/rtchost.cpp`, voir GameNetworkingSockets plus bas). `net.ini` `p2p=relay` (ou `?HK_P2P=relay` dans l'URL) : relais TURN seulement. Le lobby doit être en API 4 (`webrtc` dans les annonces) et autoriser l'origine de la page (CORS).
- **Héberger depuis le navigateur** : Server Setup → Internet `Public`/`Friends`/`Private` (comme en natif). L'onglet ouvre une session de lobby, garde le WebSocket du relais ouvert (ligne `keepalive` chaque minute, reconnexion de 1 s à 1 min), répond aux offres WebRTC des navigateurs et des versions de bureau (`hk_rtc_accept`, un DataChannel par joueur) et s'annonce `"webrtc": true, "host": "web"` (lobby **API 5**) ; jamais annoncé sans P2P. 8 joueurs au plus, hôte compris (`WEBHOSTMAXPLAYERS`). Un bandeau demande de garder l'onglet ouvert et visible : un onglet masqué ne reçoit plus `requestAnimationFrame`, la boucle passe alors sur des minuteries (environ une image par seconde dans un onglet en arrière-plan, juste de quoi garder les joueurs connectés).
- **Test** : `python3 tests/web_smoke.py [build/web] [--out dossier]` sert la build sur un port local et la joue dans Chromium sans écran par Playwright (`pip install playwright && playwright install chromium-headless-shell`) : le menu se dessine, une partie solo démarre (`HK_MENU=serverstart`), le joueur apparaît (clic) et avance, puis avance au stick d'une manette simulée (API Gamepad du navigateur), puis sur un téléphone simulé (844×390, événements tactiles) : les commandes tactiles s'affichent, un toucher fait apparaître, un doigt marche pendant qu'un deuxième regarde et qu'un troisième tire, la page ne défile pas, Menu met en pause et Resume reprend, le dossier utilisateur survit à un rechargement ; captures dans `build/web-smoke`. Avec `--lobby <edifice-lobby>` (compilé depuis `server/`), il lance aussi un lobby local sur un autre port, y annonce une partie et vérifie que l'onglet Internet la reçoit (CORS), sans jamais contacter le lobby public. La CI le fait (job `web`).
- **Test réseau** (local, pas dans la CI) : `python3 tests/net_webrtc.py build/<os>-release-gns/Edifice[.app] build/edifice-lobby [build/web] [--relay]` lance un lobby local (HTTP sur 127.0.0.1, relais WebSocket, CORS de la page, STUN/TURN sur l'adresse LAN), un hôte de bureau `HK_AUTOSTART` avec son propre dossier (`HK_USERDIR`, `servervisibility=public` vers ce lobby, ports 37220/37221) et la build web dans Chromium sans écran, qui rejoint l'hôte par son code (`HK_LOBBYJOIN`), apparaît, tire et envoie un bloc : l'hôte doit tout recevoir (`HK_NET_EVENTS`), par une connexion DTLS directe, ou par le TURN avec `--relay`. Sous macOS, `go build -ldflags=-linkmode=external` (Go 1.21 sur un macOS récent) puis `codesign -s - -f build/edifice-lobby` si le binaire ne démarre pas. Pas dans la CI : il faut la build native GameNetworkingSockets/libdatachannel et la build web dans le même job, et les tests réseau tournent en local.
- **Test de l'hôte navigateur** (local) : `python3 tests/net_webhost.py build/<os>-release-gns/Edifice[.app] build/edifice-lobby [build/web] [--relay]` : le même lobby local, un onglet qui héberge (`HK_AUTOSTART`, `servervisibility=public`), un second navigateur (son propre stockage) qui rejoint par le code, tire et envoie un bloc, puis la version de bureau (`HK_USERDIR`, ports 37320/37321, `HK_LOBBYJOIN`) qui rejoint le même code par WebRTC ; l'hôte doit voir les deux sous `0.1.x.y`, sans cookie, et le lobby lister 3 joueurs. Affiche les images par seconde de l'onglet hôte. Le jeu de bureau y tourne sans VSync (`HK_SHOT` à une image jamais atteinte), sinon il se fige quand l'écran du Mac est en veille.

## GameNetworkingSockets (M7, dans les releases)

GameNetworkingSockets (Valve, BSD-3), avec protobuf et OpenSSL, vient de vcpkg (fonction `gns` de `vcpkg.json`). Une fois vcpkg installé :

```bash
git clone https://github.com/microsoft/vcpkg && vcpkg/bootstrap-vcpkg.sh   # Windows : vcpkg\bootstrap-vcpkg.bat
export VCPKG_ROOT=$PWD/vcpkg
python3 build.py --package                       # build/<os>-release-gns, comme la release
python3 build.py --universal --package           # macOS : binaire universel, comme la release
```

Avec GameNetworkingSockets vient **libdatachannel** (MPL 2.0, avec libjuice, usrsctp et plog : fonction `webrtc` de `vcpkg.json`, option CMake `EDIFICE_WEBRTC`) : un hôte de bureau accepte aussi les joueurs du navigateur (M14, tâche 3). `--no-webrtc` le laisse de côté (`build.py` reconfigure un dossier déjà configuré quand l'option change). Coût : environ 2,7 Mo de plus pour le binaire macOS arm64 (11,4 → 14,1 Mo).

Le premier build compile OpenSSL, protobuf et abseil (de quelques minutes à une demi-heure selon la machine), ensuite le cache binaire de vcpkg sert. Triplets : `x64-linux-release` (statique), `x64-windows-release` (`cmake/triplets/`, DLL : tout le jeu passe au runtime C++ partagé `/MD`, et les DLL du runtime sont copiées à côté de `Edifice.exe`), `universal-osx` (`cmake/triplets/`, statique, arm64 + x86_64) ; en Debug, ceux par défaut de vcpkg. `-DVCPKG_TARGET_TRIPLET=…` dans `EDIFICE_CMAKE_ARGS` en impose un autre. À la main : `cmake -S . -B build/gns -DEDIFICE_GNS=ON -DVCPKG_MANIFEST_FEATURES=gns -DCMAKE_TOOLCHAIN_FILE=<vcpkg>/scripts/buildsystems/vcpkg.cmake` (Windows : `-DVCPKG_TARGET_TRIPLET=x64-windows -A x64`). Sans l'option, rien ne change, sur le fil non plus.

`python3 tests/check_package.py dist/Edifice-<version>-<os>.<ext> --gns` vérifie une archive comme la CI : contenu et licences, dépendances (`otool`, `readelf`, `dumpbin`), puis le jeu décompressé lancé en serveur GameNetworkingSockets, avec son propre dossier utilisateur et `servervisibility=lan`, et `tests/net_handshake.py` contre lui ; `--lobby <edifice-lobby>` y ajoute un lobby local en HTTPS (certificat auto-signé, `openssl`) où le jeu doit s'annoncer et ouvrir sa session P2P (la CI le fait sous Linux) ; `--no-run` saute le lancement (écran verrouillé sous macOS : le rendu bloque).

- `transport=gns` dans `net.ini` (ou `HK_TRANSPORT=gns`) : les parties par IP directe passent par une connexion GameNetworkingSockets chiffrée (`src/net/gnslink.cpp`, choix des liens dans `src/net/netlink.cpp`). L'hôte écoute en plus sur `gnsport` (défaut : `datasendport`, 27021) ; un client se connecte au `gnsport` du serveur qu'il interroge par IP. La recherche LAN et les pairs en UDP simple restent en UDP : un serveur en mode gns accepte aussi les clients UDP. Défaut : `transport=udp`.
- Parties Internet en P2P (M7d, `src/net/gnssignal.cpp`, détails dans `docs/M7.md`) : un hôte annoncé sur le lobby (`servervisibility` autre que `lan`) écoute aussi les connexions P2P sous l'identité de sa session de lobby ; le client qui rejoint une partie de l'onglet Internet (ou par son code) ouvre sa propre session et s'y connecte par ICE (STUN/TURN du lobby, signalisation par le lobby), avec repli sur l'UDP direct. Aucun port à ouvrir, même avec `transport=udp`. `net.ini` : `p2p=1` (défaut), `p2p=0` (jamais : UDP direct comme en M7c), `p2p=relay` (seulement le relais TURN du lobby) ; `HK_P2P` a priorité. `HK_GNS_DEBUG=1` affiche les messages de GameNetworkingSockets (ICE compris).
- Joueurs du navigateur (M14, tâche 3, `src/net/rtchost.cpp`, avec `EDIFICE_WEBRTC`) : tant qu'un hôte écoute en P2P, les offres WebRTC (`rtc1:`) que le relais de signalisation lui transmet créent une connexion libdatachannel (mêmes STUN/TURN que GameNetworkingSockets, relais seul avec `p2p=relay`), qui répond et prend le DataChannel du navigateur. Le joueur arrive sur l'info link de l'hôte sous une pseudo-adresse `0.1.x.y`, comme un client P2P GameNetworkingSockets (`0.0.x.y`), sans cookie de connexion (DTLS a prouvé qui il est). L'hôte s'annonce `"webrtc": true` (lobby API 4). Dans l'autre sens, une partie listée `"host": "web"` (hébergée dans un navigateur, API 5) se rejoint par WebRTC seulement : le jeu de bureau fait alors l'offre lui-même (`RtcHostConnect`, DataChannel `edifice` non ordonné, `maxRetransmits` 0) et ses messages passent par le même info link puis par son data link à l'ENTER. `HK_RTC_DEBUG=1` affiche les messages de libdatachannel (ICE compris) et la paire de candidats retenue.
- `python3 tests/net_p2p.py build/gns/Edifice <edifice-lobby> build/gns/gns_p2p_test` : lance le lobby avec son TURN sur l'adresse LAN de la machine (GameNetworkingSockets n'utilise jamais les adresses de bouclage pour ICE), puis deux fois, en direct puis en relais TURN seul : deux processus `tests/gns_p2p_test.cpp` (`GnsLink` seul), puis un hôte du jeu et un client qui le rejoint par son code de partie (Linux, avec `xvfb-run` ; macOS avec `NET_P2P_GAMES=1`). Tout tourne sur une machine, donc sans NAT entre les joueurs : sont testés la signalisation, ICE, le relais TURN et le jeu par-dessus, pas la traversée de NAT elle-même.
- `tests/run_gns_netplay_test.sh build/gns/Edifice build/gns/gns_netplay_test` : deux clients C++ (`tests/gns_netplay_test.cpp`, `Sock` sur `GnsLink`) rejoignent un serveur en mode gns, reçoivent LANDINFO, jouent et parlent près de l'hôte ; puis une deuxième instance du jeu le rejoint (`HK_JOIN`) ; puis les tests UDP (`run_netplay_tests.sh`) contre des serveurs en mode gns.

Format réseau (protocole 5) : aucun struct n'est copié tel quel sur le fil ; chaque message a ses fonctions d'écriture et de lecture explicites (`Sync*` dans `src/net/netmsg.h` et `landwire.h`, `WriteSimple`/`ReadSimple` dans `src/net/sock.cpp`, primitives dans `src/net/wire.h`). Changer un de ces formats impose d'incrémenter `EDIFICE_PROTOCOL_VERSION` (`src/net/version.h`).

## Fuzzing

Un harnais libFuzzer par parseur d'entrée réseau ou fichier, dans `tests/fuzz/` : `Sock::Receive` (découpage des datagrammes, transferts fiables, ACK, alimenté sans socket par `Sock::Feed`), chaque message (`fuzz_position`, `fuzz_firegun`, `fuzz_killedposition`, `fuzz_updateserverobject`, `fuzz_snapshot`, `fuzz_servervars`, `fuzz_rgd`, `fuzz_landinfo`, `fuzz_simple`, `fuzz_hello` pour REQUESTENTER/INFO et le trailer de version, `fuzz_playernames`, `fuzz_chat`, `fuzz_blocks`, `fuzz_voice`) et les cartes (`fuzz_map`, `fuzz_map_legacy`). Les parseurs sont dans `src/net/netmsg.h`, `landwire.h`, `voicemsg.h`, `version.cpp`, `sock.cpp` et `src/game/mapfile.cpp`, appelables sans le jeu.

```bash
cmake -S . -B build/fuzz -G Ninja -DEDIFICE_FUZZ=ON -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++
cmake --build build/fuzz --target fuzz
ctest --test-dir build/fuzz -R '^fuzz_'          # chaque corpus de départ une fois
mkdir -p /tmp/c && cp tests/fuzz/corpus/fuzz_map/* /tmp/c
build/fuzz/fuzz_map -max_total_time=60 /tmp/c    # fuzzing (le corpus grandit dans /tmp/c)
```

- Avec un clang qui a libFuzzer (Linux, ou `brew install llvm` sur macOS : `-DCMAKE_CXX_COMPILER=$(brew --prefix llvm)/bin/clang++`), les harnais sont compilés avec `-fsanitize=fuzzer,address,undefined`. Apple clang n'a pas libFuzzer : les harnais sont alors des programmes qui passent une fois les fichiers ou dossiers donnés (`tests/fuzz/fuzz_main.cpp`), avec AddressSanitizer et UBSan.
- Corpus de départ dans `tests/fuzz/corpus/<harnais>/`, produits par les écrivains du jeu : `fuzz_make_seeds tests/fuzz/corpus` et `map_test --write tests/fuzz/corpus/fuzz_map tests/fuzz/corpus/fuzz_map_legacy`. `NET_JOIN_DUMP=<dossier> python3 tests/net_join.py` enregistre en plus les messages et datagrammes envoyés par un vrai serveur.
- La CI (job `fuzzing`, ubuntu-22.04, clang) passe les corpus puis fuzze chaque harnais 60 s ; un crash fait échouer le job et l'entrée fautive est publiée en artefact (`fuzz-crashes`). Pour la rejouer : `build/fuzz/fuzz_<nom> <fichier>`.

Le job `web` compile aussi la version web à chaque push et PR (`build.py --web --test --package`, emsdk épinglé par `EMSDK_VERSION`), puis la joue dans Chromium sans écran (`tests/web_smoke.py`) ; le site zippé (`edifice-web`) et les captures (`web-shots`) sont gardés comme artefacts.
```
src/game/      boucle de jeu, terrain (land*), structures, physique, config, vector, hugekilla.cpp
src/render/    rendu (redrawing), renderer.h (API du rendu : primitives en lots, états, matrices ; renderer.cpp),
               backend OpenGL fixe renderer_gl.cpp + texture_gl.cpp + rcontext_gl.cpp (seuls fichiers qui appellent gl*, rbackend.h),
               ou sokol_gfx (HK_RENDER_SOKOL) renderer_sokol.cpp + texture_sokol.cpp + sokol_native.cpp (rsokol.h), shaders/ ;
               rcontext.h : ce que la fenêtre demande au backend (drapeaux SDL, contexte ou device, présentation),
               rmath.h (matrices 4x4), textures (registre textures.h, image.cpp = stb_image), modèles .cob (ase, models.h)
src/net/       sockets UDP (sock), protocole et serveur/client (multiplay*)
src/ui/        menus en jeu, console, Options, Server Setup, crédits
src/audio/     sound_sdl.cpp (son SDL), voice.cpp (chat vocal opus)
src/platform/  platform_sdl.cpp : main SDL (fenêtre et son contexte par rcontext.h, entrées, dossiers ; platform.h) ;
               gamepad.cpp : manettes (SDL_GameController, gamepad.h) ; touch.cpp : commandes tactiles (touch.h) ;
               system_sdl.cpp : horloges (hktime.h), touches tenues (hkkeys.h), boîtes de message ;
               hktypes.h : DWORD/WORD/BYTE ; hksocket.h : sockets (Winsock / POSIX) ;
               gl.h : OpenGL et GLU (pour le seul backend du rendu) ; fileio.* : accès aux fichiers (std::filesystem, stdio) ;

src/third_party/ stb/stb_image.h v2.30 (nothings/stb 31c1ad3, domaine public / MIT, licence dans stb/LICENSE)

```

Un seul chemin de code : `main()` est celui de SDL sur les trois systèmes (`SDL2main` fournit `WinMain` sous Windows). Le build Win32 natif d'origine (WinMain/WndProc, DirectSound, boîtes de dialogue, menus, variante serveur dédié `HKDS`, projet Visual Studio 2003) n'était plus compilé : il a été retiré (M12.3), il reste dans l'historique git.

Chaque `.cpp` inclut ce qu'il utilise (plus de `StdAfx.h` ni d'émulation Win32) : les types `DWORD`/`WORD`/`BYTE` par `hktypes.h` (gardés : `DWORD` fait 32 bits dans les structs réseau et les sauvegardes), l'horloge par `hktime.h` (`HKTicks`, `HKPerfCounter`, `HKSleep`), les codes de touches par `hkkeys.h` (`KEY_TAB`, `KEY_F1`… : les valeurs des codes VK de Windows, que `control.ini` désigne par leur nom), les sockets par `hksocket.h`, le rendu par `renderer.h` (OpenGL, par `gl.h`, n'est inclus que par `renderer_gl.cpp` et `texture_gl.cpp` ; les API de sokol_gfx que par `sokol_native.cpp` et `sokol_gfx_impl.cpp`), et les globales partagées par le header du module qui les définit (`land.h`, `playing.h`, `multiplay.h`, `redrawing.h`, `models.h`, `ui.h`, `platform.h`…), déclarées une seule fois : pas d'`extern` local dans un `.cpp`.

## Données

`EnterDataDir` (`src/platform/platform_sdl.cpp`) cherche `control.ini`, dans l'ordre : premier argument, `HUGEKILLA_DATA`, `<dossier de l'exécutable>/data` (= `Contents/Resources/data` dans le bundle), puis `data/` du dépôt (builds Debug seulement).

Les réglages que le jeu réécrit (`control.ini`, `net.ini`, `sv.ini`) et les captures d'écran (`screenshot-*.bmp`) sont dans le dossier utilisateur, copiés depuis `data/` au premier lancement : `~/Library/Application Support/Edifice` (macOS), `%APPDATA%\Edifice` (Windows), `~/.local/share/Edifice` (Linux). Le dossier de données (et le `.app` signé) n'est jamais modifié ; supprimez un fichier du dossier utilisateur pour revenir aux valeurs par défaut.

Les données viennent de Windows (insensible à la casse) : le code écrit ses chemins en `/` et passe par `src/platform/fileio.h` (`HKReadFile`, `HKFileOpen`, `HKListDir`…), qui hors Windows retrouve un chemin sans tenir compte de la casse quand il n'existe pas tel quel (`structures` → `Structures/`). Les images (`.bmp`, et aussi `.png`/`.tga`) sont décodées par stb_image, les `.pxr` (brut, avec alpha) par `LoadRaw`. Les `.ini` et `Structures/*.txt` sont en CRLF et le code s'appuie sur le `\r` : `.gitattributes` marque `data/**` en `-text`.

## Écrans ajoutés

- **Server Setup** (bouton Server) : nom du serveur, mode (capture du drapeau / bac à sable), captures pour gagner, limite de temps, ciel, relief, décor, carte ; « Random » pour ciel/relief/décor et bouton « Randomize all ». « Map » : « New random » (un nouveau terrain, par défaut) ou une des cartes sauvegardées (voir plus bas), qui apporte alors son ciel, son relief, son décor et ses bâtiments. Sauvegardé dans `sv.ini` / `net.ini` (`servermap`). Clavier : Haut/Bas (ou Tab) choisit une ligne, Gauche/Droite la change, Entrée démarre, Échap revient.
- **Join a game** (bouton Play) : onglets LAN / IP (IP ou nom d'hôte, recherche LAN) et Internet (parties publiques du lobby, code de partie). Clavier : Tab passe d'un champ à l'autre, Entrée ajoute l'adresse / cherche le code ou rejoint le serveur choisi, Haut/Bas choisit, F5 rafraîchit, Échap revient.
- Tous les écrans 2D (menu principal, Join, Server Setup, Options, Credits, menu de construction, scores, chat, textes du HUD) écrivent avec la police du jeu en espacement proportionnel (`UIText` dans `src/ui/ui.cpp`, chasse mesurée sur la texture de la police) et partagent les mêmes panneaux et boutons (`UIPanel`, `UIButton`, `UIField`) ; seule la console garde une police à chasse fixe. La fenêtre est « high-DPI » (`SDL_WINDOW_ALLOW_HIGHDPI`, `NSHighResolutionCapable` ; sous Windows `permonitorv2` + `SDL_HINT_WINDOWS_DPI_SCALING`) : le rendu se fait à la taille réelle en pixels (2x sur Retina, captures `HK_SHOT` comprises), la mise en page reste en points.
- **Options** : touches, vidéo/audio (plein écran, VSync, distance d'affichage, souris, volume, volume des voix, micro), nom du joueur, manette et commandes tactiles (onglet Pad / Touch, voir « Manettes » et « Écrans tactiles »).
- Effets visuels (M13.5, côté client seulement, rien ne change sur le fil), chacun dans Options → Video/Audio et `control.ini` : « Gun over walls » (`fxviewmodel`, 1 par défaut) dessine l'arme en dernier, sur un tampon de profondeur effacé et avec sa propre projection (champ fixe de 70°, indépendant du zoom, plan proche à 0,02) : elle ne rentre plus dans les murs ni dans le relief, et garde l'éclairage et le brouillard de la scène. À 0, l'arme est dessinée dans la scène comme avant. « Explosions » (`fxexplosions`, 1 par défaut : « New ») : les grenades explosent en boule de feu (bouffées additives qui grandissent et refroidissent du blanc au rouge), éclair, étincelles, débris qui retombent et rebondissent, et une lueur brève sur le relief autour ; « Classic » (0) garde la gerbe de particules d'origine. « Smoke » (`fxsmoke`, 1 par défaut) : une fumée qui reste quelques secondes après une explosion « New » (bouffées qui grandissent, montent, dérivent et s'éclaircissent) et une traînée derrière les grenades en vol. « Impacts and splashes » (`fximpacts`, 1 par défaut) : une balle qui touche l'eau fait des ronds, des gouttes et un peu d'embruns, puis laisse un sillage de bulles sous l'eau ; sur le relief, un nuage de poussière et quelques grains (gris et quelques étincelles sur un bloc, vase et bulles au fond d'un lac) ; une grenade qui tombe dans l'eau éclabousse, et explose sous l'eau en bulles et en gerbe d'eau au lieu d'une boule de feu. À 0, les impacts d'origine (petits éclats bruns). « Muzzle flash » (`fxmuzzleflash`, 1 par défaut) : une lueur additive (une gerbe orange irrégulière et un cœur blanc) autour du sprite de tir pendant ses 80 premières millisecondes, pour tous les joueurs. Les effets sont dans `src/render/effects.cpp` (textures procédurales, emplacements `TEX_FX0`…), déclenchés par le jeu (`playing.cpp`).
- **Credits** : auteurs originaux.

## Cartes sauvegardées

Le terrain (relief, ciel, décor) et tous les bâtiments, dans `maps/<nom>.map` du dossier utilisateur (voir Données). Commandes de console (`` ` ``) :

- `savemap <nom>` : enregistre la partie en cours (serveur ou client) ; le nom ne contient que lettres, chiffres, `_` et `-` (32 au plus), un fichier existant est remplacé ;
- `loadmap <nom>` : sur le serveur, remplace le monde par la carte pour tout le monde (les clients la reçoivent comme un nouveau terrain : LANDINFO, puis tous les blocs) ; hors partie, démarre un serveur avec cette carte ; refusé quand on est client d'un autre serveur ;
- `maps` : liste les cartes enregistrées.

Un serveur lancé avec une carte (`loadmap` ou Server Setup) la recharge à chaque nouvelle manche, avec ses bâtiments d'origine. Debug : `HK_AUTOSTART=1 HK_MAPFILE=<chemin absolu>` démarre le serveur avec ce fichier (le jeu se place dans son dossier de données : un chemin relatif partirait de là).

Format 2, décrit dans `src/game/mapfile.h` : en-tête `EDIFICEMAP`, version du format, protocole (informatif) et dimensions de la grille, puis le ciel, les `LandDefs` et les blocs écrits champ par champ en little-endian, en plages de cellules identiques (quelques Ko pour un monde peu construit), et un CRC-32. Un fichier tronqué, trop gros, corrompu, d'un autre format ou d'une autre taille de monde est refusé avec un message ; les noms de textures et les compteurs sont bornés comme ceux d'un message LANDINFO. Les sauvegardes du jeu d'origine (Windows, 2000 : `edifice` suivi des structs brutes, environ 55 Mo) se chargent aussi : les copier dans `maps/` avec l'extension `.map`. Leur relief, leur ciel et leurs bâtiments sont repris ; le décor (arbres, taches du sol) diffère, le générateur du monde ayant changé au protocole 3.

## Chat vocal

Push-to-talk de proximité : maintenir `T` (Options → Controls → « Push to talk », `pushtotalk` dans `control.ini`) pour parler. Seuls les joueurs à moins de 40 unités vous entendent (la distance d'affichage est de 57) : plein volume jusqu'à 8 unités, puis de plus en plus faible, et la voix vient de la position du joueur (gauche/droite). Toutes équipes confondues. Constantes dans `src/audio/voice.h`.

- Capture SDL 48 kHz mono ouverte au premier appui, active seulement pendant l'appui ; trames opus de 20 ms (~24 kbit/s) envoyées en non fiable (message `VOICE`, `src/net/voicemsg.h`).
- Le serveur remplace le numéro de joueur par celui du client, ignore les joueurs hors partie et ne relaie qu'aux joueurs proches ; l'hôte entend directement les clients proches.
- Réception : un décodeur opus et un petit tampon de gigue par joueur (ordre par numéro de séquence, trames en retard ou en double ignorées, trame perdue masquée par opus), mixés dans le callback audio (`src/audio/sound_sdl.cpp`, désormais à 48 kHz).
- HUD : « Mic on » pendant l'émission, « Speaking: nom » pour les joueurs entendus.
- Options → Video/Audio : « Voice volume » (`voicevolume`, 0–100) et « Microphone » (`voicemic`, 0/1).
- macOS demande l'accès au micro au premier appui (`NSMicrophoneUsageDescription` dans `cmake/MacOSXBundleInfo.plist.in`). Sans micro ou sans autorisation, rien n'est émis (message unique sur stderr).

## Manettes

`src/platform/gamepad.cpp`, par `SDL_GameController` : toute manette de la base de SDL (Xbox, PlayStation, Switch Pro, 8BitDo…), branchée ou débranchée à tout moment (message dans la console ; rien ne reste appuyé quand elle part). Une manette inconnue est signalée sur stderr avec son GUID : sa ligne de [SDL_GameControllerDB](https://github.com/mdqinc/SDL_GameControllerDB) dans un `gamecontrollerdb.txt` du dossier utilisateur (ou de `data/`) la fait reconnaître. `A` est toujours le bouton du bas (`SDL_HINT_GAMECONTROLLER_USE_BUTTON_LABELS=0`). Sur le web, l'API Gamepad du navigateur passe par le même SDL (Emscripten).

- **En jeu** : le stick gauche fait marcher en analogique (`SetPadMove`, `playing.cpp` : la vitesse suit l'inclinaison, jamais plus vite qu'au clavier ; les drapeaux avant/arrière/côtés envoyés sur le fil sont ceux du clavier, sur huit secteurs : aucun changement de protocole), le stick droit fait regarder (envoyé comme des comptes de souris, indépendant de la sensibilité de la souris ; vertical à 70 %). Les boutons appuient la touche de leur action (`controls`), donc font exactement ce que fait le clavier. Gâchettes : appuyées au-delà de la moitié, relâchées sous le tiers. Vibration courte quand on est touché (si la manette en a et `pad_rumble=1`).
- **Boutons par défaut** (`pad_*` de `control.ini`, noms de SDL ; Options → Pad / Touch pour les changer : cliquer l'action, puis appuyer le bouton) : `RT` tir, `LT` jetpack (et planeur, liés au même bouton droit de la souris par défaut), `A` saut, `B` prendre/poser (en posant une structure : annuler), `X` recharger, `Y` construire, `RB`/`LB` arme suivante/précédente (en boucle ; en posant une structure : la tourner), `R3` zoom (tenu : le stick droit règle le zoom, comme la souris), `Back` scores, croix haut/gauche/bas : parler, parler à l'équipe, push-to-talk, `Start` menu (Échap).
- **Réglages** (Options → Pad / Touch, `control.ini`) : sensibilité du regard (`pad_sensitivity`, 1 ≈ 180°/s), zone morte radiale (`pad_deadzone`, 18 %), courbe de réponse (`pad_curve`, 1,6 : puissance de l'inclinaison, plus fin au centre), regard inversé (`pad_invert`), vibration (`pad_rumble`).
- **Menus** : croix ou stick gauche (répétés quand on les tient) déplacent un focus (cadre jaune) entre ce qui se clique ; `A` clique dessus (deux fois de suite : double-clic, pour rejoindre une partie de la liste), `B` ou `Start` font Échap, `Y` ferme le menu de construction. Sur une ligne à valeur (Options, Server Setup), gauche/droite cliquent ses « < » et « > ». Le focus disparaît dès que la souris bouge ou qu'on tape au clavier. Mécanique (`src/ui/ui.cpp`, logique pure dans `src/ui/inputlogic.h`) : chaque widget cliquable enregistre sa zone en se dessinant (`UIButton` le fait seul, les écrans ajoutent leurs lignes, onglets et listes par `UIFocusable`), le pad choisit la zone voisine dans la direction (`InFocusNext`) et clique en plaçant `mousepos` en son centre : les écrans n'ont rien d'autre à savoir. Les champs de texte se focalisent mais demandent un clavier.

## Écrans tactiles

`src/platform/touch.cpp` : une manette à l'écran, surtout pour la version web sur téléphone et tablette (les écrans tactiles natifs aussi : Windows, Linux). Elle apparaît au premier toucher d'un doigt sur l'écran (seulement les appareils « directs » de SDL : pas le trackpad d'un Mac) et s'efface dès que la souris bouge, qu'on tape au clavier ou qu'on appuie sur une manette. Options → Pad / Touch : « Touch controls » (`touchcontrols` : 1 au premier toucher, 2 toujours, 0 jamais) et « Touch controls size » (`touchsize`, 60 à 160 %).

- **En jeu**, plusieurs doigts à la fois : un doigt posé sur la partie gauche y place un stick de déplacement (analogique, comme celui d'une manette : `SetPadMove`), un doigt sur la partie droite fait regarder en glissant (≈ 80° pour la hauteur d'un téléphone), et les boutons appuient la touche de leur action : Fire (on peut viser en glissant le doigt qui tire), Jump, Jet (jetpack et planeur), Reload, Weapon (arme suivante, en boucle), Zoom (tenu : glisser règle le zoom), Claim, et en haut Build, Scores, Menu. En posant une structure : Place, Turn (la tourner), Cancel. L'écran d'apparition joue au premier toucher ; en pause, le bouton Menu devient Resume.
- **Menus** : un toucher clique là où le doigt se lève (deux de suite au même endroit : double-clic) ; glisser fait défiler le menu de construction. SDL ne fabrique plus de souris à partir des doigts (`SDL_HINT_TOUCH_MOUSE_EVENTS=0`) : `touch.cpp` fait les clics lui-même, et un doigt sur un bouton du jeu ne tire ni ne clique au travers. Les champs de texte n'ouvrent pas le clavier du téléphone.
- **Tailles** en points de la fenêtre (pixels CSS sur le web), que le système met déjà à l'échelle de l'écran : le bouton Fire fait environ 14 mm sur un téléphone ; une petite fenêtre réduit tout pour tenir (`InTouchLayoutFor`, `src/ui/inputlogic.h`, testé par `tests/input_test.cpp`).
- **Page web** (`shell.html`) : pas de défilement, de zoom ni de sélection sur la page (`touch-action: none`, `user-scalable=no`, `viewport-fit=cover`), un bouton « Full screen » (sous la barre de vie, au premier toucher, là où le navigateur a l'API Fullscreen ; puis paysage verrouillé où c'est permis, Android), et « Turn your device sideways to play » quand l'appareil est tenu droit.

## Aides au debug

- `HK_AUTOSTART=1` démarre un serveur local directement (avec `HK_MAPFILE=<fichier .map>` : sur cette carte).
- `HK_ZOOM_TEST=1` simule un appui sur la touche de zoom (zoom ×3).
- `HK_SEED=N` génère le même monde à chaque lancement (pour comparer des captures).
- `HK_PADTEST="300:axis:lefty:-1;390:log;400:press:a;…"` : appuis de manette scriptés, à la N-ième image (`Frame()`), par une manette virtuelle de SDL (`SDL_JoystickAttachVirtual`, comme une vraie : correspondance, événements, branchement), ou par des événements poussés sans elle. Étapes `F:press:NOM` (appui puis relâchement 4 images après), `F:down:NOM`, `F:up:NOM` (boutons de SDL, `lefttrigger`, `righttrigger`), `F:axis:NOM:V` (`leftx`… de -1 à 1, gâchettes de 0 à 1), `F:log` (état sur stderr : position, cap, arme, tir, menus, focus…), `F:shot:NOM` (image dans `HK_PADSHOTS/NOM.ppm`), `F:unplug`/`F:plug`, `F:finger:N:down|move|up:X:Y` (doigt N d'un écran tactile en X,Y, de 0 à 1 dans la fenêtre : événements SDL poussés, appareil `TOUCH_TESTID`). Les événements de manette sont aussi reçus fenêtre inactive. Utilisé par `tests/input_smoke.py`.
- `HK_KEYLOG=1` affiche dans le terminal chaque touche reçue par le jeu (code de `hkkeys.h`, celui des touches VK de Windows) et les changements de zoom.
- `HK_MENU=options|options2|options3|player|credits|join|internet|server|serverstart` ouvre cet écran au démarrage (`options3` : l'onglet Pad / Touch) (`internet` : l'onglet Internet de Join) ; `build`, `scores` et `chat` démarrent un serveur local et ouvrent le menu de construction, les scores ou le chat.
- `HK_LOBBYJOIN=<code>` cherche ce code de partie sur le lobby (`net.ini` `lobby=`) et rejoint la partie, par l'onglet Internet (en P2P si elle a une identité, voir GameNetworkingSockets).
- `HK_P2P=0|1|relay` remplace `p2p=` de `net.ini` ; `HK_GNS_DEBUG=1` affiche les messages de GameNetworkingSockets, `HK_RTC_DEBUG=1` ceux de libdatachannel (pont WebRTC d'un hôte). `HK_NET_EVENTS=1` (serveur) écrit sur stderr les tirs et blocs des clients dès leur arrivée (`tests/net_webrtc.py`). `HK_SIGNAL_TCP=1` : signalisation par le relais TCP même si le lobby propose son relais WebSocket (`wss://`). `EDIFICE_TEST_CA_FILE=cert.pem` (tests seulement) : certificat PEM d'un lobby auto-signé, accepté en plus de ceux du système pour le lobby et la signalisation (la vérification reste faite).
- `HK_CONSOLE=1` démarre un serveur local et ouvre la console après quelques commandes (`help`, `maps`, …) ; `HK_CONSOLE=scroll` la fait défiler vers le haut, `HK_CONSOLE=notify` la laisse fermée (dernières lignes sur le jeu), toute autre valeur reste tapée à l'invite (`HK_CONSOLE=gr` : complétion). Avec `HK_CONSOLE`, `HK_CONSOLE_RUN="savemap essai;loadmap essai"` exécute en plus ces commandes (séparées par `;`), par exemple pour vérifier l'aller-retour d'une carte dans `maps/` du dossier utilisateur.
- `HK_SHOT=fichier.ppm` (et `HK_SHOT_FRAME=N`) enregistre l'image rendue N (sans VSync : sous macOS, l'échange d'images attend sinon indéfiniment quand l'écran est en veille).
- `HK_PLAY=1` : apparaît en jeu dès que l'écran d'apparition s'ouvre, comme son bouton Play (captures en jeu sans le panneau, avec `HK_AUTOSTART=1`).
- `HK_FRAMETIME=N` : affiche sur stderr le temps moyen des N images (300 par défaut) qui suivent l'image `HK_SHOT_FRAME` (120 par défaut), sans VSync, à l'horloge réelle même avec `HK_FIXEDCLOCK` (comparaison des rendus).
- `HK_FIXEDCLOCK=N` : l'horloge du jeu avance de N ms par image dessinée au lieu de suivre le temps réel (caméra, nuages, animations et compteur d'images répétables d'une exécution à l'autre, pour les pixel-diffs du rendu ; `16` ≈ 60 images/s). Le réseau garde l'horloge réelle.
- `HK_USERDIR=<dossier/>` remplace le dossier utilisateur (`control.ini`, `net.ini`, `sv.ini`, cartes) : des essais (captures, taille de fenêtre `screenwidth`/`screenheight`) sans toucher aux vrais réglages.
- Pixel-diff du rendu (M12.5, M13) : capturer les mêmes écrans (`HK_MENU=…`, `HK_CONSOLE=notify`, `HK_AUTOSTART=1 HK_MAPFILE=…`, avec `HK_SEED`, `HK_SHOT_FRAME` et un `HK_USERDIR` fixes) avec l'ancien et le nouveau binaire, puis `python3 tests/pixel_diff.py avant/ apres/` (tolérance 0 par défaut, `--tolerance N`, `--diff d.ppm` pour une paire). Les écrans 2D doivent être identiques ; les images en jeu varient d'une exécution à l'autre (caméra et animations suivent l'horloge) : `--ignore avant2/` (une deuxième capture de l'ancien binaire, répétable) ignore les pixels qui changent déjà entre deux exécutions de la référence. Avec `HK_FIXEDCLOCK=16`, la plupart des captures en jeu deviennent identiques d'une exécution à l'autre (il reste des écarts quand la souris bouge sur la fenêtre, ou quand le ciel tiré au hasard change) : comparer plusieurs exécutions de chaque binaire et retenir, pour chaque image, la capture de référence la plus proche.
- Chat vocal : `HK_VOICE_TEST_TONE=1` émet une tonalité à la place du micro, `HK_VOICE_AUTOTALK=1` émet en permanence (sans touche), `HK_VOICE_LOOPBACK=1` fait entendre sa propre voix par le chemin de réception, `HK_VOICE_LOG=1` affiche sur stderr chaque début de prise de parole entendue.
